# Architecture

## Deterministic agent runtime

The built-in workflows now enter one persistent server-side runtime instead of loading sources directly in the HTTP route. A versioned `AgentDefinition` registry declares objective, status, allowed sources, skills, tools, planner, memory scopes and risk classes. The standard path is definition → policy evaluation → allowlisted read tools → bounded context snapshot → active scoped memories → deterministic planner → proposal → persistent run and steps → optional memory candidate → content-light audit. The existing workflow response remains compatible and adds honest runtime evidence.

`lib/runtime/` contains definitions, registries, bounded context selection, planning, policies, skills, tools, receipts, model boundaries, scheduler evaluation and orchestration. Runtime SQL is confined to `lib/repositories/`; services do not issue SQL. Field encryption and generic transaction execution have dedicated `lib/store/` boundaries while the established shared-store remains the compatibility facade for older domain repositories. Additive migrations 9–14 extend the same database—there is no second store—with encrypted context payloads, ordered run steps, structured memory/events, execution receipts, persisted schedules, a reconstructable runtime status and ordered invocation lifecycle events.

Only `deterministic-local` planning and skills are executable. `model-assisted` exists solely as a disabled contract and fails closed. The tool registry contains fixed internal reads only; there is no generic HTTP tool dispatcher. Existing stricter Calendar and Obsidian approval services remain separate and authoritative.

Memory is structured and provenance-bearing. Content and provenance are AES-256-GCM encrypted. Retrieval is deterministic: active, unexpired global memory plus matching agent, project and area scopes allowed by the agent definition. Agent-generated observations remain candidates. Agents cannot create policy memory or activate/reject any candidate; review is an authenticated, same-origin, version-checked user mutation.

Google Calendar separates bounded reads, exact proposal creation, and execution. OAuth grants only `calendar.calendarlist.readonly` and `calendar.events`; it does not grant ACL/sharing, settings, delete, or broad calendar administration. Encrypted proposal tokens contain one exact create/update, expire after 15 minutes, require a second literal confirmation, perform idempotency checking, and append a metadata-only local audit record after success.

SQLite is the **current** source of truth for mutable operational state, not the accepted end state. The laptop uses the bundled Node 24 `node:sqlite` driver, versioned transactional migrations, WAL, parameterized queries, field-level AES-256-GCM for sensitive values, and private authenticated same-origin APIs over localhost/Tailscale only. Updates and reversible archives require the exact structured row version; stale clients receive HTTP 409, reload current state and never silently overwrite a newer client. Database files, WAL/SHM, backups, and keys live under git-ignored local state. Client localStorage is inventoried and compared through a review-only conflict preview before any import. A PostgreSQL-compatible server is being evaluated for laptop-independent access; `infra/postgres/` is a loopback-only, unstarted schema PoC with no user-data migration. See `docs/DATA-SERVER-EVALUATION.md`.

The Emre Obsidian vault is the durable, human-readable knowledge/document source of truth behind the Agentic OS UI. Agent-owned notes use stable IDs, typed frontmatter, provenance, timestamps, relationships/backlinks, status, privacy, and append-only audit metadata. Existing notes remain unchanged until an exact normalization preview, backup plan, and user approval. Sensitive knowledge follows Inbox → review/normalize → approved write. Google Calendar remains the external event source of truth.

Next.js is the single shared UI and server source of truth. It can run in three local clients without duplicating product screens: a normal browser/PWA, a hardened Electron desktop window, and an Expo Go mobile WebView pointed at the same laptop over the local network. Modules use one shared state envelope for inbox items, approvals, branding/theme preferences, and audit records. Settings can create local SQLite snapshots with SHA-256 metadata and preview their integrity, schema and record-count conflicts. There is deliberately no restore executor yet.

All sensitive operational API methods enforce the signed local session before validation and use `Cache-Control: no-store, private`, including reads and mutations for records, preferences, audit, backups, migration preview and Calendar proposal/write. Missing authorization is uniformly a 401 and never falls through to a misleading validation response.

Archive is a normal reversible record state, not deletion. A separate content-light signed endpoint lists archived metadata and restores one exact row version transactionally to the status retained in its stored payload. Related project or agent dependencies must be restored first. Database backup restore remains absent and separately gated.

The Electron main process starts a loopback-only Next development server on port 3210, waits for readiness, and then opens it in a sandboxed window. The renderer has context isolation, no Node integration, guarded top-level navigation, denied permission requests, and no cloud dependency. The current deliverable is a verified development shell, not a packaged installer.

The Expo SDK 54 companion is intentionally minimal because current Expo Go physical-device compatibility requires that SDK during the SDK transition. Its only runtime configuration is the non-secret `EXPO_PUBLIC_AGENTIC_OS_URL`, set dynamically by the Windows launcher to the current LAN address or verified private Tailscale Serve URL. The WebView accepts its configured origin, routes external HTTPS links to the operating system, and provides branded loading, invalid-config, connection-error, and retry states. No EAS account, public tunnel, build, update, or hosting service is used.

Private remote access adds no public ingress. A production Next process binds only to `127.0.0.1:3211`; Tailscale Serve terminates HTTPS on the laptop's MagicDNS name and makes it reachable only under the tailnet access policy. Funnel is never invoked. Expo Go development advertises Metro on the dynamically discovered Tailscale IPv4 while the WebView uses the private HTTPS URL. The laptop must remain awake; Run Unattended and power behavior stay user-controlled.

The connector boundary is intentionally separate from planning logic. A connector exposes `connect`, `read`, `previewWrite`, `commitApprovedWrite`, and `disconnect`. Agents can read normalized calendar/task records and produce proposals, but only the approval service can issue a write token. Every token is single-use, scoped to a displayed change set, and recorded in audit history.

The knowledge adapter accepts a configured directory, inventories Markdown without writes, previews frontmatter/wiki-links/tags, and only then builds an application-owned index. Obsidian is the human-readable knowledge and notes layer, not the operational database. Structured tasks, approvals, project state, audit records, connector state, agent handoffs and shared theme preference belong in the authenticated application store. SQLite is the operational bridge; a PostgreSQL-compatible server is the proposed end state. Synchronization to Obsidian remains deliberate, previewed, approved and audited.

The live Obsidian index is server-only and read-only. `lib/obsidian-vault.ts` inventories bounded Markdown metadata and local relationships from a runtime-configured path; `app/api/obsidian/status` returns sanitized health/index evidence without absolute paths, bodies, or frontmatter values. A separate proposal-only module can construct exact new-note or missing-frontmatter diffs for validated indexed targets. It rechecks hashes, conflicts, backup and restore evidence and can only reach `approved_pending_apply`; there is no Apply endpoint or write primitive. See `docs/OBSIDIAN.md`.

Google Calendar routes are server-only. Credentials never enter the browser bundle. Tokens are encrypted in local ignored state and HTTP-only sessions; status, catalog, bounded reads, OAuth entry and local token sharing additionally require the signed private app session and use private no-store responses. The OAuth callback instead verifies its own encrypted ten-minute state. Disconnected production routes return empty/unavailable results and never inject test events; old mock HTTP proposal/approval paths are retired. Calendar/event routes normalize Google records and enforce an eight-day window. The granted scopes are calendar-list read access and event access only—no ACL, sharing, settings, delete or broad administration. Create/update uses an exact expiring proposal, literal per-action approval, idempotency check, read-back and audit. The one explicitly approved test event was completed; the UI now prepares no further write by default.

## Expanded application

The command center routes one shared local state into domain dashboards for faith, career, health, finance, relationships, and projects. Faith prayer/Qurʾān fields, health training/recovery/nutrition values, manual financial numbers and relationship dates/constellation positions are explicit validated fields inside encrypted `area_records`; the public row contains only identifier, area, type, title and status. Dashboards derive summaries/charts only from present records and otherwise show empty states. Journal, tasks, habits, inbox, agents, skills, chats, integrations, and knowledge remain cross-domain services. Branding is preference data—not a schema identifier—so the temporary product name can change safely.

Project resources are deliberately metadata-only. They reuse validated project-linked Inbox records: a short operational title remains queryable while the `http(s)` URL or inert local file reference is field-encrypted. The project UI can reveal that text on demand but contains no file open, copy, upload, preview or filesystem inventory primitive.

Custom Agent records are configuration only: name, purpose, allowlisted life areas, paused/metadata-only status and either no provider or manual ChatGPT Companion mode. The records route validates that no API model, paid provider or executable status can be selected. The five built-in local-rule workflows remain a separate, explicitly invoked proposal layer with their own encrypted run history.

The model console has three user-facing honest states: ChatGPT Companion Mode as the default subscription workflow, optional OpenAI Responses API, and an optional local model only after runtime verification. Mock policy remains a test fixture, not a claimed usable provider. Companion Mode opens ChatGPT for conversation and keeps Agentic OS responsible for projects, tasks, knowledge, dashboards, tracking, and visualizations. It has no automatic access to ChatGPT conversation history. The only transfer is a user-selected summary pasted into the local Inbox. The server-side provider guard rejects requests unless API mode, server key, positive spend ceilings, and a disabled kill switch are all explicit.

The Emre vault is the human-readable source of truth. Its additive numbered indexes use stable `type` and `schema_version` frontmatter and link to existing area notes without replacing them. Application writes remain preview → approval → audit. The built-in graph derives from frontmatter and Wikilinks. Graphify is non-core and limited to a future pinned TypeScript pilot on a non-sensitive copy with structural extraction only.
# Deterministic Skill/Tool Execution (August 2026)

The runtime now turns deterministic planner decisions into structured skill invocations. Skills execute through the existing local procedure catalog and may call only fixed, bounded, read-only tool executors. Skill and tool invocations become ordered, content-light run steps; full source records remain in the encrypted context snapshot and are not copied into audit metadata.

Each completed synchronous Skill/Tool invocation also persists the deterministic lifecycle `planned → validated → started → completed`. Policy/execution failures persist a content-light failed Runtime run whenever the agent and local store are known, without copying the rejected input into plaintext evidence.

The Agent and standalone Skill APIs share the same execution service and procedure catalog. The six built-in agents declare objective, boundary, sources, skills, tools, planner, memory, permission and context policy. The Weekly Planner uses trusted connector data only after the existing bounded Google read, then runs `weekly_plan` through six read tools and persists normal Runtime evidence before producing the existing encrypted weekly-plan proposal.

Receipts distinguish proposed/not-started, blocked, started, confirmed, failed and unknown execution, with explicit retry policy. Calendar remains stricter than the generic contract: exact encrypted payload, 15-minute expiry, single use before transport, idempotency, read-back verification and manual verification for unknown outcomes. Vault receipt mapping is preparation-only; no Vault apply exists. Five explicit local mutation tools are available only behind the signed same-origin `user_direct_intent` API and optimistic versions; agent proposals/schedules cannot invoke them.

The provider-neutral model layer describes capability, privacy, latency, structured-output and cost requirements. A deterministic fake adapter exists only for tests. The production router has no active provider, and the OpenAI adapter boundary performs no transport even when configuration gates are inspected. Structured proposals are schema-, size-, agent-, skill-, tool- and risk-validated before any future Runtime execution.

Persisted daily/weekly schedule definitions contain encrypted input and a deterministic Europe/Berlin due calculation. Evaluation is an explicit private API action; there is no timer, daemon or OS background host. Only read/proposal agents can be scheduled, and approvals can never be bypassed.

The productive path is: agent definition → policy → scoped context → deterministic planner → skill invocation → allowlisted read tools → local skill result → proposal → persistent run steps → content-light audit. It performs no model, network, file, background, or external-write action.
